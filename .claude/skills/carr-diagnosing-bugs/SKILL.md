### 1c21263c

REWORK IS A SIGNAL THE SESSION READS ON ITSELF, NOT ONE IT WAITS FOR A PARTNER TO NOTICE. When the same SHAPE of problem needs fixing about four times in one stretch of work, stop and fix the instruction rather than the fourth instance. The count is the trigger. Four attempts at one thing is a defect in what the session was told, not a shortfall of effort, and grinding out the fifth is the expensive way to learn that.

WHAT COUNTS AS THE SAME SHAPE, since this is useless if it only fires on identical errors: the same class of fix landing in different files (three test files each hardcoding a $HOME path), the same artifact wrong in a new way each round (a lockfile fixed twice, for platform markers and then for staleness), or the same build-and-check cycle failing on a fresh cause each time (four CI runs to reach green). All three happened on 2026-08-13.

THE ACTION WHEN IT FIRES: name the pattern out loud to the partner, write the durable fix — a rule, a check, a template, a shared helper — and only then continue. A check is better than a rule, because a check fires without anyone remembering. What must NOT happen is the session quietly absorbing the rework and reporting only the finished result: the partner then sees a clean outcome and never learns the process was broken.

A system that only learns when a human catches it repeating itself learns at human speed.
