## 3. Patches applied before comparison

Investigation (documented in full in this seat's build receipt,
`out/frontier-finding/build-receipts/slice-compare/RESULT.md`) found the
raw baseline diff was dominated by two renderer defects -- one on each
side -- rather than genuine coverage gaps, plus one PARSED-side
under-modeling of ACL no-op semantics. All three were fixed with minimal,
documented patches and the affected side regenerated/re-rendered. No
database connection was opened by this seat at any point.

**3a. PARSED-side patch** (`parse_extract_targets.py` in this directory,
regenerated by re-running the script against the same pinned commit via
`git show` -- no other input):

1. `function:`/`grant:`/`revoke:`/`comment:` identities for functions now
   retain the parameter NAME alongside the type (e.g. `p_epoch bigint`,
   not `bigint`) and canonicalize the one type alias present in this
   corpus (`timestamptz` -> `timestamp with time zone`), matching the
   real, empirically-verified behavior of `pg_get_function_identity_
   arguments()` -- cross-checked against all 109 functions' own CREATE
   FUNCTION parameter lists at the pinned commit; the old parser
   stripped names and kept the raw SQL type keyword, which the identity
   contract's own reference implementation (`pg_get_function_identity_
   arguments`) does not do.
2. `COMMENT ON FUNCTION` and `GRANT`/`REVOKE ... ON FUNCTION` statements
   use a genuinely type-only argument list in real SQL grammar (verified
   against the migration text itself); these are now resolved against
   the canonical name+type signature already captured from that
   function's own CREATE FUNCTION statement (`FUNCTION_SIGNATURE_INDEX`),
   instead of being emitted as their own, differently-shaped identity.
3. A cross-file rename-forwarding pass for `COMMENT ON FUNCTION` targets:
   this corpus's "successor" idiom renames a bare function name forward
   across later files (e.g. `scac_policy_epoch_snapshot()` -> `_v3` in a
   later file); a real Postgres COMMENT follows the object's OID through
   that rename, which a single-pass-per-file extractor cannot know about
   until the rename statement is reached. Scoped to niladic functions
   (the only case exercised in this corpus, verified by grep).
4. Cumulative ACL-state tracking for REVOKE: a `REVOKE ALL ... FROM
   <roles>` naming a role that was never actually granted the privilege
   (per the GRANT/REVOKE statement order already visible in the
   migration text) removes nothing in a real database and produces no
   observable diff. The patch tracks granted/revoked state per (object,
   grantee, privilege) across all 18 files in statement order and
   suppresses REVOKE emission when nothing is currently granted. GRANT
   emission is left unfiltered (zero redundant re-grants occur in this
   corpus, verified).

**3b. OBSERVED-side patch** (`gen_frontier_manifest.py`'s `diff_comments`
in this directory, patched but never re-run against a database; the
equivalent correction applied to the delivered artifact by
`rerender_observed_comments.py`, which reads ONLY data already captured
in the manifest itself):

The function branch of `diff_comments` built its identity from
`pg_identify_object()`'s `identity` column (a dead `if False:` branch in
the original showed a correct path had been drafted and never wired in).
`pg_identify_object()` renders function identities with fully
schema-qualified built-in type names (e.g. `pg_catalog.text`) and WITHOUT
parameter names -- inconsistent with the `function:` identity form used
everywhere else in the SAME manifest (`pg_get_function_identity_
arguments` via the pg_proc family). Fixed by resolving each function
comment against the already-known-correct `function:` target for that
schema-qualified bare name (no function in this corpus is overloaded --
verified: zero (schema, name) collisions across the 109 real functions,
so bare-name resolution is unambiguous).

### `constraint_trigger_pg_constraint_dual_registration`

Direction: observed_only. Matched: 18 (expected 18).

New finding: PostgreSQL registers a CONSTRAINT TRIGGER (as opposed to a plain TRIGGER) as BOTH a pg_trigger row and a pg_constraint row (contype='t'), under the same name. PARSED correctly captures all 18 of these as trigger: targets (matched, not in either diff) via its documented CREATE [CONSTRAINT] TRIGGER handler; it has no principled textual signal that the SAME statement also produces a second, independent pg_constraint-family catalog row. Verified by enumerating every CREATE CONSTRAINT TRIGGER statement across all 18 pinned files (git show) and confirming an exact 1:1 name match against these 18 observed-only constraint: targets, plus confirming an 18th entry (doctrine_gate_check) that coincidentally also matches the auto-name suffix pattern '_check' was correctly attributed here and not to auto_named_constraint_scope_decision.

### `auto_named_constraint_scope_decision`

### `implicit_backing_index`

Direction: observed_only. Matched: 84 (expected 84).

New finding, same class as implicit_composite_array_types: every PRIMARY KEY or UNIQUE constraint (named or unnamed) implicitly creates a backing btree index carrying the constraint's own name. PARSED emits zero index: targets by design, since an exhaustive grep of migrations/0454-0471 confirmed zero literal CREATE INDEX statements -- but it does not additionally model the implicit index PostgreSQL creates for every PK/UNIQUE constraint. Verified: 83 of 84 targets' index name exactly matches a PARSED-known or auto-named PK/UNIQUE constraint name (_pkey/_key suffix); the 84th (scac_mutation_registry_entry_identity_uq) is the backing index for the ONE explicitly-named unique constraint in this corpus, confirming the mechanic applies uniformly whether the constraint itself is named or auto-named.

### `implicit_composite_array_types`

Direction: observed_only. Matched: 52 (expected 52).

The observation seat's documented finding #1 (out/frontier-finding/build-receipts/slice-a/RESULT.md): every CREATE TABLE causes PostgreSQL to auto-create a companion composite row type (typtype='c', same name as the table) and an array type (typtype='b', '_'-prefixed name). No migration file contains an explicit CREATE TYPE for these. Verified: all 52 targets resolve to exactly 26 composite + 26 array types, a 1:1 pairing with the 26 table: targets PARSED and OBSERVED already agree on.

### `owner_materialization_grants`

Direction: observed_only. Matched: 316 (expected 316).

The observation seat's documented finding #2 (slice-a RESULT.md): the first explicit GRANT/REVOKE on a previously-ungranted object causes PostgreSQL to materialize the object's full ACL array, which includes an explicit entry for the object's OWNER -- in this disposable, carr_manifest (the generator's bootstrap role) -- even though no migration statement names that role. In production the owner role would differ (e.g. neondb_owner), but the *fact* of an owner-materialization grant appearing is a genuine, reproducible PostgreSQL mechanic invisible to text parsing regardless of which role happens to be the owner. Verified: all 316 remaining grant: observed-only targets share grantee carr_manifest, with no other grantee appearing. Two sub-populations: 108 function EXECUTE grants, and 208 table grants (26 tables x 8 privileges: select/insert/update/delete/truncate/references/trigger/MAINTAIN -- MAINTAIN is a PostgreSQL 15+ table privilege that PARSED's ALL_PRIVS_BY_KIND table-privilege set does not enumerate, itself a minor, separately-noted scope gap in the ALL-expansion list rather than a coverage miss, since MAINTAIN cannot appear in this corpus's text-visible GRANT/REVOKE ALL statements any more than the owner-materialization grantee can).

### `migration_runner_ledger_bookkeeping_row`

Direction: observed_only. Matched: 18 (expected 18).

New finding: each of the 18 pinned migration files, once applied by the real migration runner (tools/migrate.py, run unmodified from the pinned commit per the observation seat's method), causes the runner itself -- not any statement inside the migration file's own SQL text -- to insert one ledger row into public.schema_migrations recording that file's name/sha256/applied timestamp. The identity contract restricts the PARSED extractor to deriving targets 'ONLY by reading migrations/0454-0471' (rule 1); this row insert is not literal text in any of those 18 files, so it is categorically outside the extractor's permitted read scope, not merely difficult to parse. Verified: exactly 18 targets, one per pinned migration file, each attributed (per the OBSERVED by_file map) to precisely the file it was inserted after.
