## 1. The finding of record

**Within this Work Request's authority, no safe workaround exists for the parked production migration lane. Bounded claim: the enumerated families below, disposed on execution-verified evidence, plus a standing boundedness rule — not a proof over an open universe.**

1. **The runner-register family fails.** (Review one, B1–B9, execution-verified.) The first frontier file is the sole creator of registry tables nine later files depend on; a skip strands the lane one file later. Synthetic ledger rows spoof at least eight filename-existence readers and permanently break the ledgers-identical-by-construction release invariant. The register's own grammar pins objects absent on production AND every disposable at decision time (B3); an observed-side pg_catalog probe differs (600 vs the pins) but was order-unstable in-run with no expected-value authority, and B4–B9 bind regardless. Pending selection never re-offers a ledgered filename: a one-way door.
2. **The pre-frontier insertion family fails.** (Review two, N-B1–N-B5, execution-verified.) The slot regex captures only four digits, so every letter file needs a per-slot amendment to the frozen-exceptions register — inverting its purpose. Every post-frontier database (staging first) hard-refuses a pre-frontier file as a backward hole. On fresh builds, census-perturbing work in the namespace turns every disposable red, reported as the frontier failing. An applied probe file can never be removed.
3. **The remaining families dispose as follows:**
   - **A production-only executor with a separate receipt ledger is not an exit.** Built safely it mechanizes F01 (same authority, same conditions, same admissible class — by B2 plus the census constraints, excluding the frontier set and nearly all post-frontier files); built unsafely it is break-glass minus the control. No such tooling ships here.
   - **Rebasing/re-pinning the registry migrations against production's catalog** is the leading candidate mechanism for the frontier program's OWN activation, not a workaround: v1–v9 are source-only, the generator exposes rebased-write commands through v10 (ops/scac-mutation-inventory.mjs ~1988–2059), and its embedded constants come from disposable readback (its comments say so) — a production re-pin needs a measurement stage that does not exist yet. F02 enumerates what exists and names that stage as the activation program's work. Sealed means APPLIED history; unapplied source is regenerable by design.
   - **Holding all merges** is containment, not an exit. Refused as strictly worse than F01 plus the countdown.
   - **Boundedness rule (doctrine):** new candidate families are filed on WR-000046 and disposed under the same execution-verified discipline BEFORE any build.
4. **Therefore the exit is the integrity program's production activation — and its first problem is the bootstrap ordering circle:** production's pending selection stops at 0454, so a successor after 0471 never runs while the frontier is pending. Activation must (a) regenerate/re-pin the source-only frontier set against production's live catalog (writers + the missing measurement stage, under its own chain) or (b) bootstrap out-of-band under its charter's receipts. That choice — with the reconciliation matrix and dead-end catalog — is the decision F02 delivers to Joe. The frontier files' text keeps production application Joe-gated; that authority stays where it lives.

**Artifact C — the receipt instrument: `breakglass-run.py` (driver) + `gen-breakglass-run.py` (per-use generator) + `breakglass-snapshot.sql` (snapshot queries).** Deliberately an INSTRUMENT, not a load-bearing gate:
- **Execution path:** `CARR_BREAK_GLASS=1 .venv/bin/python tools/db-tap.py --reason "<WR note ref>" run docs/frontier-finding/breakglass-run.py -- --approved <run>.sql --receipt <receipt>.json` — db-tap's `run` mode executes the driver with the derived DATABASE_URL and no DSN on a command line. ONE psycopg connection; `BEGIN ISOLATION LEVEL REPEATABLE READ` (one MVCC snapshot for the whole run — concurrent commits cannot leak into the pre/post comparison); pre-snapshot queries; the approved candidate SQL; post-snapshot queries; delta computed in the driver; COMMIT only when the assertions hold, else ROLLBACK.
- **Approval oracle (named):** Joe's approval is a RECORDED WR-000046 note (record-layer write, timestamped, attributable) carrying the run-script sha256, candidate sha256, and manifest sha256. The driver prints the digests it computed; the operator compares against the recorded note before confirming, and the receipt cites the note. The oracle is the record layer, not the file system; a run whose digests do not match the recorded approval is a protocol violation on its face and any later auditor can recompute both sides.
- **Receipt durability ordering:** the driver writes the receipt in TWO phases — the pre-phase receipt (candidate, manifest, identity, pre-snapshot WITH full pre-images for declared targets) is written to disk and fsynced BEFORE the candidate executes; the outcome phase (post-snapshot, verdict, sequence report) is appended after commit/rollback. The driver fsyncs both the receipt file and its parent directory before the candidate executes, reducing the crash exposure to the filesystem's own durability guarantees — stated as that, not as an absolute. The full JSON lives in `out/break-glass-receipts/` beside the existing break-glass log, and its sha256 goes into the WR-000046 note; the note is the durable pointer of record.
- **Identity tuple:** the receipt records `(endpoint_host from conn.info.host, database_name, pg_system_identifier)` — all three observed from the LIVE CONNECTION by the driver itself, none from arguments (the db-tap wrapper does not pass its --branch argument through, so nothing claims it does). Neon endpoint hosts are unique per endpoint, which is exactly the branch axis: a different branch is a different endpoint host. Restore mode refuses unless ALL three match.
- **Snapshot surface (reviewed, extendable, NOT claimed complete):** full rows (minus a short named volatile-statistics exclusion list) of pg_proc, pg_class (incl. relrowsecurity, relforcerowsecurity, reloptions), pg_attribute, pg_attrdef, pg_constraint, pg_trigger (incl. tgenabled), pg_policy, pg_rewrite, pg_default_acl, pg_namespace, pg_roles, pg_auth_members, pg_extension, pg_index (with pg_get_indexdef), pg_sequence (FULL configuration row — start, increment, min, max, cycle — plus last_value and is_called), pg_type and pg_enum, pg_partitioned_table; the five Section-0 census row-sets; per-table row digests over all user-schema tables. The surface list is part of the reviewed artifact PR and is extended freely as gaps are found; Section T carries the residual. Effects on this surface that were not declared abort the run — that claim is scoped to the surface, exactly.
- **Transaction-control preflight:** the generator reuses `tools/migrate.py`'s `contains_transaction_control()` verbatim (covers COMMIT/ROLLBACK/END/ABORT/START TRANSACTION/PREPARE TRANSACTION; passes dollar-quoted PL/pgSQL bodies — the migrate-precondition selftest proves both directions).
- **Three-sided assertion:** (1) EXPECTED-PRE PRECHECK — before the candidate runs, each declared target's observed pre-state must equal the manifest's declared expected PRE-state (a wrong assumption about what is being changed is caught before anything executes, and a candidate expected to change something that is already in its intended post-state is surfaced, not silently passed); (2) no undeclared change on the snapshot surface; (3) each declared target equals its declared expected POST-state.
- **Sequence honesty (corrected):** the snapshot includes full `pg_sequence` configuration plus `last_value`/`is_called`, so ANY sequence change — forward advancement, `setval` backward, `is_called` flips, configuration edits — is OBSERVED and REPORTED in the receipt. `nextval`/`setval` effects survive rollback by PostgreSQL design and are never described as rolled back. NO automatic benign classification: the receipt reports every sequence delta and the HUMAN reviewing the receipt classifies it in the WR note (forward gaps from declared inserts are the expected benign case; anything else is presumptively an incident). A backward `setval` is exactly the duplicate-key hazard the report exists to surface.
- **Restore mode (restoration ASSISTANCE, honestly scoped):** `gen-breakglass-run.py --restore <receipt>.json` generates a restore run for a NAMED receipt. Identity predicate: the full identity tuple must match AND the receipt's candidate sha256 must match the incident's named row. COMPARE-AND-SWAP guard: for each declared target, the restore run's own pre-state must equal the receipt's recorded POST-state — if the target has legitimately changed since the incident row landed, the restore REFUSES rather than overwrite later work, and the incident escalates to a designed manual forward fix. Restoration is generated from pre-images where the lifecycle permits (definition texts re-applied; row values re-written by key for rows that still exist); lifecycles the pre-images cannot mechanically regenerate (dropped objects with dependent state, identity/generated columns, trigger-mediated cascades, absent pre-images) are NAMED in the incident as manual-forward-fix territory. The doctrine text says exactly this: value-level restoration assistance for declared targets when the world has not moved; designed forward fixes for everything else.

## 3. Rollback, failure modes, and recovery — stated honestly

**Reverts:** doctrine sections by version; the docs PR and repo pointer by revert commit; artifacts by regeneration from the pinned commit.
**Does not revert:** Model Room events (superseded, never deleted); landed break-glass rows (permanent history — forward-only recovery: restoration assistance under restore mode's guards, designed forward fixes where those guards refuse); sequence changes (non-transactional by PostgreSQL design; observed, reported, human-classified).
**Failure modes:** *Normalization* — every use requires a fresh recorded approval note; the instrument makes undeclared surface effects abort; approvals and refusals leave WR notes; incidents on violation; the protocol names its own end state. *Later-discovered wrong state* — incident; restoration assistance where the compare-and-swap and lifecycle guards admit it; designed forward fix, honestly named, where they do not. *Incorrect readback* — snapshots recomputable; supersede with a corrected pair. *Activation stall* — the WR-000046 queue is the visible countdown; each break-glass use re-surfaces the DECISION_REQUIRED; escalation pressure, not resolution. *Partial activation* — detectable (conjunct (i)/(iii) fails); pre-activation baseline plus the activation program's rehearsed abort/repair define reference and path; F01 freezes to restorative-only meanwhile. *Dead-end rediscovery* — the catalog is doctrine; the runbook forbids rebuilding buried families.
**Reopens if:** the integrity program's activation design concludes a bounded runner mechanism is safe after all — through its own chain, with these reviews as prior art.
