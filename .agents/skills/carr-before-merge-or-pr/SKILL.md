### 1c42d80c

ALWAYS FIX THE THING; A WORKAROUND IS NOT A FIX. Binding at the moment a session hits friction it did not expect: a refusal, a false alarm, a command that has to be reshaped to get through, a diagnostic that prints the wrong thing. Fix the CAUSE, in that same session, rather than routing around it.

A workaround is recognisable by what it leaves behind: the system still does the wrong thing, and only this session knows the trick. Stripping a link to satisfy a guard, passing a skip flag, rerunning with different wording, hand-editing a generated file, or handing the friction to a partner instead of removing it are all the same move. Each one leaves the next session to pay the same cost, and it compounds because nobody files it.

The standard is one fix at a time, permanently. If the friction is real then something in the system is wrong and can be corrected: a host missing from an allowlist, a writer missing from a registry, an accumulator that never resets, an interpreter without the module it needs. Name that thing, fix it, ship it with a test that fails first, and the friction never returns.

A workaround is acceptable only to unblock the immediate step, and only when the real fix ships in the same session. If the real fix genuinely cannot ship, the session says so plainly and files it — it never goes quiet.

### 347a9ca6

A SESSION'S NAME DOES NOT PREDICT THE WORK IT WILL DO. Joe works INSIDE routine and scheduled sessions, and turns them into full build sessions. His correction, 2026-08-09, after a session claimed routine sessions "call verbs and never touch the working tree": "thats not true. i often work inside a routine session like the nightly record layer. we actually did a significant amount of work in that session just today." Confirmed against the record the same minute: the session titled "Loop cleanup and deferral policy" was concurrently doing system-design work — reasoning about hook tracking, git-clean exposure, and untracked gates — none of which its name suggests.

SO THERE IS NO SUCH THING AS A "ROUTINE SESSION" IN THIS SYSTEM. There are scheduled STARTS. What happens after the start is whatever Joe decides to do in that window, and he decides often. A session named nightly-record-layer, loop-cleanup, social-batch or x-reply-run may write code, redesign a mechanism, or teach a rule.

THE DETECTABLE MOMENT is any point where a session is about to reason FROM ITS OWN NAME, or from another session's name, to a conclusion about the work. Concretely: deciding whether to isolate in a worktree, deciding how much context to load, assuming another session is "only calling verbs" and therefore safe to write around, sizing a concurrency risk, or judging whether the git working tree is contended. In every one of those, the name is not evidence. Look at what the session is DOING — its actual tool calls, its dirty paths, its transcript — or treat the work shape as unknown.

THE FAILURE THIS PREVENTS is not hypothetical. It produced a wrong recommendation within one turn: a session argued against per-session worktrees on the reasoning that "most sessions don't edit code — nightly record layer, loop cleanup, social batch call verbs and never touch the working tree." The premise was false, so the recommendation rested on nothing, and Joe had to correct it himself. Any design that partitions sessions into a code-editing class and a safe class is built on this same false premise and should be re-derived from observed behaviour instead.

THE CORRECT TRIGGER IS THE SHAPE OF THE WORK, NEVER THE LABEL. A multi-hour build touching many files wants isolation whatever the session is called; a three-verb record update does not, whatever it is called. Judge by what is happening.

### 3578d799

NAME VERBS AND SYSTEM NOUNS IN HUMAN WORDS, NOT MACHINE OR DATA-PIPELINE WORDS. This is the verb-layer companion to the agent-naming rule (#c6f69dee, "Content Writer" over write-content): a human should be able to tell what a verb does from its name without reading its description. The existing verb set already follows this — teach, find, catch-me-up, who-do-we-know, stamp-touch — and a word borrowed from data engineering reads as foreign next to them. The specific ruling that set this: the proposed verb for absorbing an outside source was going to be called "ingest," and Joe replaced it with "study." The rename is not cosmetic. "Ingest" means swallowing something whole, which is precisely what the knowledge policy forbids (no verbatim, transcribe-distill-discard, merge to domain shape). "Study" means reading something, judging it, keeping what is useful and leaving the rest — which is the actual policy. When a name and a doctrine disagree, sessions drift toward the name, so the name has to carry the doctrine. Test before naming anything: would a person outside this system guess what it does, and does the word describe the behavior the doctrine actually requires? If a proposed name fails either test, rename it before it ships, not after it has spread through migrations, exports and prose.

Joe's ruling 2026-08-08: if Doc is not perfect, Dell will never use him and Joe will eventually tire of him too. A voice colleague nobody reaches for is worth nothing regardless of how much engineering went in, so the quality bar is not "good enough to ship" but "good enough that two busy brokers choose it unprompted, for years." THE BINDING CONSEQUENCE, and the behavior this rule exists to correct: NEVER propose a workaround when the real fix is available and merely harder. When a capability is missing, the first move is to find tooling that HAS it — not to design around the gap, not to approximate it with what is already installed, not to reframe the constraint as a feature. Cheapness, install friction, an unfamiliar dependency, and "we already have X" are all insufficient reasons to accept a lower ceiling. Cost is a tiebreaker between paths that both reach the bar; it is never a reason to lower the bar. THE PATTERN THAT PROMPTED IT, recorded so it is recognizable next time: in one session the host proposed a two-voice architecture (a fast stranger for novel speech, Doc's real voice only for cached lines — killed by council as trust-inverting), then proposed per-register reference anchors as a way to live with an engine that silently discards delivery instructions, and in the same breath framed a genuinely better engine's speed as a drawback when it was in fact FASTER than the status quo (CosyVoice2 at ~20s/line vs Doc's ~31s/line, presented as a catch). Both moves optimized for effort rather than outcome; Joe caught both. THE TEST BEFORE PROPOSING ANY COMPROMISE: would a busy partner, using this daily for a year, notice and resent the gap? If yes, it is not a compromise, it is a defect, and the search for real tooling continues. "we go all out" is the standing posture for Doc specifically and for anything else whose value depends on a human choosing it voluntarily. Composes with the dialogue-mode metric already in doctrine (records logged by voice per partner per week, Dell's tracked from his day one; if his number stalls, "the failure is in this spec, not in Dell — find the friction, fix the moment, never fix the user with a rule") and with the recovered 2026-08-01 critique that the core premise stays untested until Dell actually lives in it.
