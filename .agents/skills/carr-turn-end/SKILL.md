### 19ebbeb3

A DETECTED BUG IS RECORDED AND ADDRESSED IN THE SAME SESSION, NEVER STEPPED OVER. Binding at the moment a session notices anything broken while doing something else: a gate that fires wrongly, a test that pins the wrong thing, a verb that refuses with an error naming no field, a reader that files duplicate loops, a merge conflict the file's shape keeps causing, a seat that cannot deliver its report. The session does not note it in chat and keep going. In that same turn it (1) records the defect with record-defect, and (2) either fixes it on the spot when the fix is small and inside its own authority, or files a Work Request with report-problem naming the product task it blocks and dispatches or queues the fix. Mentioning a bug to Joe is not addressing it; a defect row with no fix and no Work Request is a bug the system has agreed to live with, and nobody agreed. The system itself owes the same discipline: every recorded defect without a linked Work Request or fix receipt is surfaced by the nightly chain until one exists. ### 1b8e7f43

A BLOCKED ACTION IS FILED, NEVER DROPPED. When a session cannot do something because the capability is withheld — a verb missing from its profile, a human-gated verb, a permission it does not hold, a credential only a partner has — it MUST open a loop recording what needs doing, for whom, and the evidence it already gathered. The block means "not by you, not now." It never means "this did not need to happen."

WHY THIS IS A RULE AND NOT AN INSTINCT: every guard in this system is designed to STOP a wrong write, and stopping is the easy half. None of them is designed to remember. So the natural behaviour of a well-guarded session is to be prevented, explain itself once in a chat nobody rereads, and move on — and the work evaporates with the session. That is worse than the write it was stopped from making, because a wrong write is visible and correctable while lost work is neither. The away-mode profile carries `add-loop` for exactly this reason: the capture verb sits INSIDE the restricted profile on purpose, so being blocked is never an excuse for leaving no trace.

WHAT THE LOOP MUST CARRY, because a loop that says "could not create party" is nearly as lost as no loop: the specific action, the subject it concerns, WHY it was blocked (which profile, which verb, which gate), and the evidence already collected so whoever picks it up does not redo the research. Where a decision is owed rather than an action, use marker `decision` so it surfaces as a question rather than a task.

THIS BINDS EVERY SESSION, not only away mode. A scheduled run on the capture profile that finds a duplicate it cannot merge, a delegated seat that cannot fire a write verb under 75c2e4c9, a session that hits a humanOnly verb or a classifier-blocked migration — all of them file the loop and then report. Report AND file; reporting alone is the failure this rule closes, because chat is not a record.

ORIGIN, Joe 2026-08-03, on being told the away profile deliberately cannot create a party: he did not ask for the restriction to be loosened. He asked for the work to survive it.
