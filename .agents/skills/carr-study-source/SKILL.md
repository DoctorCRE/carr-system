### 466a545a

When Joe feeds a source, the job is to IMPROVE the system with it, and the burden of proof sits on "we already do this." Reading in full is not studying: grade every claim by testing the system against the source's ACTUAL standard, property by property, and the test for each principle is "name what this source does that we cannot do today." Pattern-matching a source's concept to a similar-shaped mechanism we already have and declaring validation is the banned move — a "mostly validates us" verdict is the SUSPECT outcome that triggers a re-grade, never the comfortable default. Filing a source as confirmation is dismissal wearing a compliment. The deliverable of a source study is the list of things it would change about our system, with each declined item carrying the specific property test it failed — not a scorecard of resemblances. ### 94806da2

FOR ANY SOURCE THAT WILL CHANGE DOCTRINE, RULES, OR RECORDS, READ THE RAW BYTES — never let a fetch tool's summary layer be the only reader. Proven necessary 2026-08-06 night: WebFetch's extraction model FABRICATED most of an arxiv paper — a confident, detailed, entirely invented architecture (fake enforcement components, fake three-tier timeouts, fake 94% accuracy metrics), none of it in the actual PDF. The fabrication was caught only because the reader pulled the saved raw PDF and read all seven pages directly. The procedure: when a source feeds a capture, a doctrine merge, a taught rule, or a record write, fetch the raw artifact (PDF pages read directly, raw HTML/markdown from the canonical host, repo files over landing pages — the 12-factor "site" was a contentless shell whose real content lived in its GitHub repo) and cite section/page anchors from the raw read. A fetch-tool summary is acceptable for triage and for answering a passing question; it is never acceptable as the sole basis for anything durable. This is verify-the-artifact (fa217e48) applied to reading: the summary layer is a subagent whose claims about a source require the source itself, and an extraction model under pressure to answer will invent a plausible paper rather than admit it could not parse one.

### 9e3fb6d0

WHEN JOE SHARES INDUSTRY CONTENT FROM A COLLEAGUE OR COMPETITOR, RUN BOTH PASSES: INGEST THE SUBSTANCE SO IT CAN BE APPLIED, AND ANALYZE THE CRAFT WITHOUT EVER COPYING IT. Pass one, the knowledge: extract the operating insight, paraphrase it to domain shape per the knowledge policy, and merge it into the playbook or SOP where it will actually fire during work. Never store it verbatim, never create a per-producer file. State plainly which file it landed in. Pass two, the craft: separately observe HOW the piece was built and delivered, including structure, paragraph rhythm, the emphasis devices used, length, how it opens and closes, and the graphic or visual treatment. File that as an observation in the visual-style/craft layer, explicitly labeled as observation. NEVER reproduce the layout, the format, the visual template, or the signature devices, and never quote or reference the source publicly. The point of pass two is to understand why a format works for its audience and whether that reasoning transfers, not to imitate a colleague. Both passes run by default on a shared link; do not do only the substance half.
