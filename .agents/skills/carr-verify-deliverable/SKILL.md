### 43e2ef76

PLAN THE CHECK BEFORE YOU BUILD THE THING. On any non-trivial build, change, or deliverable (3+ steps, or anything carrying a structure or architecture decision), the session decides HOW the work will be verified BEFORE implementation starts, and states that plan to the partner alongside the build plan: which artifact will be read, what it will be compared against, and what result would count as a failure. Verification designed after the fact is designed by the session that just built the thing and wants it to pass — the same conflict 2b66211d fixes downstream with fresh-context verifiers; this rule fixes it upstream, by fixing the success criteria while they can still be wrong. A build whose check was never planned is not finished, it is unverified. Complements a9ecd5b4 (a check compares the artifact against what it SHOULD be) by scheduling that comparison instead of leaving it to the end, and fa217e48 (verify the artifact, not the summary) by naming the artifact in advance. ### a6e6ab4e

CHECK AGAINST THE BASELINE, NOT ONLY AGAINST THE SPEC. Whenever a change modifies something that already worked, verification includes a before-and-after comparison — the prior behaviour, output, count or render set beside the new one — and not only a check that the new state matches the intended specification. The two catch different failures: a specification check (a9ecd5b4) proves the change did what was asked, while a before-and-after comparison proves it did not break something nobody thought to specify. Where a real prior state exists (the previous file, the last export, the record as it stood before the write, the unmodified branch), capture it BEFORE making the change rather than trying to reconstruct it afterwards. Where no prior state exists, say so plainly rather than letting a specification check quietly stand in for one. ### a9ecd5b4

A CHECK MUST COMPARE THE ARTIFACT AGAINST WHAT IT SHOULD BE, AND A SUCCESS SIGNAL MUST BE DERIVED FROM READING THAT ARTIFACT. Binds at two named moments.

MOMENT 1 — BUILDING OR REVIEWING ANY GUARD. The test is never "is it non-empty" and never "did the command exit 0". Ask what the artifact looks like when it is RIGHT, and compare against that: a floor derived from the last known-good instance, a structural marker the producer writes only on success, a count. On 2026-08-07 bin/backup-dump.sh guarded the nightly backup with `[ -s "$OUT.tmp" ]` — more than zero bytes. pg_dump lost its Neon connection mid-dump, age encrypted the empty stream into a 200-byte file, the guard passed it, `mv` promoted it to that day's official backup, the archiver uploaded it to R2 as the durable off-Mac copy, and the dead-man switch was pinged. Nine months of nightly backups were one Neon blip away from the same fate.

MOMENT 2 — WIRING ANY SIGNAL THAT REPORTS ON WORK. A signal that reports on work it did not read is a FALSE signal and gets rewired or removed, never left in place. Three instruments agreed the backup succeeded that night and not one had read it: the healthchecks dead-man ping fired because the chain reached the end rather than because the backup was good; `set -eu` without `set -o pipefail` returned age's exit status instead of pg_dump's, so the failing stage was invisible; and the success line printed `du -h`, which floors at the 4K block size and therefore physically could not display 200 bytes as wrong. A hang is the same defect at the limit — the R2 archiver blocked for 3h20m on an untimed DB read, so the chain never returned, `set -e` never fired, and the scheduled task reported nothing at all. An exit-code check can never catch that, because there is no exit code.

THE PRACTICAL TEST, applied at build time and at review time: name the artifact, then point at the line that reads it. If no line reads it, the check is decoration and must be treated as an outstanding defect, not a passing check. Corollary for every threshold: state what the number is measured FROM, because an instrument can go on printing a confident figure long after the thing it measures stopped being the thing you care about — restore-rehearse.sh reported a backup as "28h old" from its mtime when a git history purge had rewritten the file, while the dump was seven days old.
